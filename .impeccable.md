## Design Context

### Users

Kimen is for security-minded developers, infrastructure engineers, and small technical teams who want to keep secrets local-first. They need a practical way to store encrypted secrets, project them only at runtime, and avoid ambient exposure through global shell exports, copied `.env` files, or overly broad agent/tool access.

### Brand Personality

Precise, direct, and restrained. The interface should feel operational and honest rather than editorial or salesy. It should communicate control, intent, and bounded exposure.

### Aesthetic Direction

For current exploration, create multiple genuinely different concepts around Kimen's unique model: vault first, explicit intent second, projection into the target process third. Avoid standard SaaS feature grids, gradient startup aesthetics, and superficial security tropes. Each concept can use a different visual language if it stays direct, security-minded, and specific.

### Design Principles

1. Say exactly what Kimen does in the first screen.
2. Make vault -> intent -> process the core mental model.
3. Prefer strong structural ideas over feature-card repetition.
4. Keep copy blunt, practical, and honest about limits.
5. Make the differences between concepts obvious enough that they can be evaluated side by side.
6. Avoid the default landing-page hero formula: tiny eyebrow, big left-aligned h1, supporting subhead, and generic CTA row.
7. Avoid dedicated "what it is not" sections unless they are genuinely necessary.
8. Prefer one strong diagram or object over multiple stacked sections.
9. Let geometry carry the vault -> intent -> process story whenever possible.
10. For this pass, show static config and secret values converging into standard env before the app starts.
11. Use direct plain-language product copy early, including that Kimen is local-first and that apps can stay simple if env is prepared up front.
12. Prefer utility, reference, and operator aesthetics over campaign or SaaS marketing patterns.
13. Keep diagrams reduced to the minimum number of blocks and paths needed to explain the tool.
14. For the main site, favor documentation-site simplicity similar to leiningen.org: one-column reading flow, plain links, and sections separated by rules.

How to keep local development secrets out of Git

Your application may need a database URL or API key. The repository needs to describe that requirement. It does not need to contain the value.

Kimen guide, updated September 2026

The usual solution stops at .gitignore.

A common local setup puts credentials in .env and adds that filename to .gitignore. This reduces accidental commits, but the plaintext file still lives inside the project workspace.

Any editor, script, plugin or coding agent which can read the workspace may also be able to read the file. Each developer must create a copy, keep it current and remove it when access changes.

If the file is accidentally committed, removing it in a later commit is not sufficient. Git history and existing clones may still contain the value, so the credential should be revoked or rotated.

Separate the requirement from the value.

The repository should carry enough information to explain what the application needs. The actual value should belong to the environment where the application runs.

project requirement
DATABASE_URL

local binding
DATABASE_URL → dev.database_url

local encrypted vault
dev.database_url → postgres://…

The mapping can be reviewed and committed. The database URL cannot, because it is not in the project.

Supply the value only when the program starts.

Kimen stores local values in an encrypted vault. A small map in the project connects the application variable to a vault entry:

# .kimen/profiles/dev.kmap
env DATABASE_URL=dev.database_url

Then start the application through Kimen:

kimen run --profile dev -- ./app

The application receives a normal DATABASE_URL. It does not need a Kimen library or a new configuration API. The plaintext value does not need to be stored in the project.

The receiving program can read the value.

Runtime injection reduces where secrets are stored. It does not make an untrusted child process safe. Only project values into software you trust with them.

What this changes for a development team

  • The repository documents required names without containing reusable credentials.
  • A fresh checkout does not need a copied plaintext secrets file beside the code.
  • Local tools can inspect the project structure without automatically seeing the values.
  • A developer can use separate vaults and profiles for different projects or environments.
  • Secret rotation no longer depends on finding every forgotten project-local copy.

Kimen is deliberately local and open source. Teams which already have a shared password or secrets service can keep using it. Kimen's useful boundary is the project contract and runtime projection, not ownership of every organization's secret storage.

A practical migration

Start with one non-production credential. Record the variable name in a Kimen profile, store the value in the vault and run the application through kimen run. Confirm that the program behaves exactly as before, then remove the plaintext project copy.

Do not migrate a value until you know every process which needs it. Configuration errors are easier to diagnose one secret at a time.

Clojure configuration and REPL secrets with Kimen

Keep using Aero, Environ, cprop or direct environment access. Move the secret values out of the project and supply them when the JVM starts.

Kimen guide, updated September 2026

Clojure projects assemble configuration in several ways.

Some applications read the JVM environment directly:

(def database-url
  (System/getenv "DATABASE_URL"))

Others turn several sources into a Clojure map:

  • Aero reads explicit EDN configuration and supports #env, #profile, #include and other tagged values.
  • Environ normalizes Leiningen or Boot settings, environment variables and Java system properties into one map.
  • cprop merges classpath EDN, filesystem configuration, system properties and matching environment variables.
  • Omniconf declares a configuration blueprint and can populate it from environment variables, command-line arguments, Java properties, EDN files or AWS SSM.

There are more variations, including custom EDN readers and Integrant or Component systems which receive an already assembled map. Kimen does not need to choose the application's configuration library.

In many deployed systems, the final source is still the process environment or a Java system property even when the rest of the application sees only a Clojure map. Other systems read a private file or fetch values from a remote secret manager.

The value still has to come from somewhere.

A configuration library can parse, merge and validate values. It does not remove the need for a source of authority:

  • An environment variable must be exported by a shell, process manager, container runtime or launch tool.
  • A private EDN file must exist on the developer's machine or runtime host.
  • A Java system property must be supplied when the JVM starts.
  • An application which calls Vault, AWS SSM or another secret manager still needs an identity or credential which authorizes that call.

Aero is unusually direct about this boundary. It supports #env, but recommends using environment variables sparingly and suggests a private included file for passwords because process environments can leak.

The Kimen question is not which Clojure library should win. It is where the local secret should live before Aero, Environ, cprop or the application reads it.

Kimen can supply the source your application already expects.

For environment-based configuration, keep the existing Clojure code and declare the runtime names in a Kimen profile:

# .kimen/profiles/dev.kmap
env DATABASE_URL=clojure_dev.database_url
env PAYMENTS_API_KEY=clojure_dev.payments_api_key
kimen run --profile dev -- clojure -M:dev

Aero can continue reading the environment:

{:database-url #env DATABASE_URL
 :payments-key #env PAYMENTS_API_KEY}

If the application already expects a private EDN file, Kimen can materialize one for the lifetime of the child process and expose only its path:

# .kimen/profiles/dev.kmap
file secrets.edn=clojure_dev.secrets_edn
envpath APP_SECRETS_FILE=secrets.edn
{:secrets #include #env APP_SECRETS_FILE}

The Clojure process can read the resulting values in either model. Kimen removes the need for a permanent plaintext copy inside the project. It does not hide secrets from the application which legitimately consumes them.

A workload identity may already be better.

If production can fetch a secret directly with a narrow cloud or secret-manager identity, adding Kimen to that path may offer little. Kimen is most directly useful for local development and other runtimes where developers would otherwise keep the values in shell exports or private project files.

This is how Kari starts its development REPL.

A Clojure REPL often loads the complete application. It may open a database, call external APIs or start the same integrations used by the running service. Kari is such an application, with several external services and realtime integration scenarios.

Its committed Kimen profile names the environment it expects:

# .kimen/profiles/kari-dev.kmap
env PORT=kari.dev.port
env OPENAI_API_KEY=kari.dev.openai_api_key
env AZURE_OPENAI_ENDPOINT=kari.dev.azure_openai_endpoint
env AZURE_OPENAI_API_KEY=kari.dev.azure_openai_api_key
env CSRF_SECRET=kari.dev.csrf_secret

The right side contains vault references, not the values. The same profile contains non-secret constants where the project should own the value:

env AI_CHAT_PRIMARY_PROVIDER=const:azure
env AI_CHAT_FALLBACK_PROVIDER=const:openai
env GEMINI_VERTEX_LOCATION=const:europe-west4

The development script starts nREPL as a child of Kimen. Its essential command is:

kimen run --profile kari-dev -- \
  clojure -M:dev:jvm-base \
  -m nrepl.cmdline \
  --bind 127.0.0.1 \
  --port 7888

Once the REPL is ready, the application reads normal environment variables. It has no Kimen dependency.

The same profile starts one-off scenarios.

Kari also has a Clojure scenario runner which talks to external realtime services. The runner needs much of the same configuration as the REPL, but it is a separate process:

kimen run --profile kari-dev -- \
  clojure -M:dev:jvm-base \
  -m kari.realtime-scenarios \
  dev/scenarios/realtime/production_minimal.edn

The scenario definition stays in the repository. The selected provider keys and runtime values come from the local vault when the process starts.

This avoids duplicating a large development environment in shell exports, a checked-out envfile and a separate REPL configuration. Both processes use the same declared profile.

A profile is useful documentation.

The project can review changes to variable names, constants and vault references without reviewing any secret value:

project declares
  OPENAI_API_KEY
  AZURE_OPENAI_ENDPOINT
  CSRF_SECRET

local vault contains
  the concrete development values

runtime receives
  only the profile selected for this process

A new checkout can see what Kari expects. It cannot recover the values from Git. A developer can bind the same names to their own local vault.

A long-running REPL keeps its environment.

Kimen supplies the selected values to the JVM when it starts. The REPL and code evaluated inside it can read those values for the lifetime of that process.

That is correct for a trusted application REPL. It is not isolation from code evaluated in the REPL, editor middleware attached to it or libraries loaded into the JVM.

Runtime delivery is a storage boundary.

The values no longer need to live in the repository or a plaintext project file. The receiving Clojure process still has them. Locking the Kimen session does not remove environment variables from an already running JVM.

Give the REPL its runtime without keeping the values beside the code.

Commit the profile, keep the values local and start the normal Clojure process through Kimen.

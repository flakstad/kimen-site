Runtime configuration without committing .env files

Environment variables can remain the interface to your application. Secret storage and resolution do not have to happen inside the project.

Kimen guide, updated September 2026

The application only needs the value while it runs.

A database URL is useful to a process which is opening a database connection. It does not need to sit in a project file while somebody edits documentation, reviews code or runs a formatter.

Runtime configuration separates two concerns. The project declares what the program expects. The environment decides which concrete value should satisfy that requirement for this invocation.

project
  expects DATABASE_URL

local environment
  binds DATABASE_URL to dev.database_url

runtime
  receives the resolved value

Start with a normal application.

Your code can continue to read an ordinary environment variable:

DATABASE_URL

Create a Kimen vault and store the value. Kimen prompts for it so the credential does not need to appear in shell history:

kimen vault init
kimen secret set dev.database_url

Then add a committed profile which contains the variable name and reference:

# .kimen/profiles/dev.kmap
env DATABASE_URL=dev.database_url

Project the value into one trusted process.

kimen run --profile dev -- ./app

Kimen opens the vault, resolves the profile and starts ./app with DATABASE_URL in its environment. The application does not need to know that Kimen was involved.

This is different from exporting a secret into the parent shell. The value is supplied to the child process for that invocation instead of becoming ambient configuration for every later command in the terminal.

Use the projection the receiving software expects.

Environment variables are common, but some programs require a file or standard input. Kimen can resolve the same local vault into several runtime forms:

# environment variables for a child process
kimen run --profile dev -- ./app

# private runtime files
kimen render --dir ./runtime --profile dev

# an envfile for a process manager
kimen envfile --out .env.runtime --profile worker

Rendered files and envfiles contain plaintext by necessity. Put them in a private runtime directory, restrict permissions and remove them when the receiving software no longer needs them.

Use short sessions for several invocations.

A Kimen session avoids typing the vault passphrase for every command:

kimen session start --ttl 15m
kimen run --profile dev -- ./app
kimen session lock

An active session widens the local boundary. A process running as the same operating-system user may be able to use the session. Prefer a short lifetime and keep the vault locked while untrusted same-user tools have unrestricted access.

Runtime delivery is not isolation.

The receiving process gets the selected values and can copy them. Use kimen run for trusted software. Kimen Operations explores a different model for callers which need one bounded result rather than the credential itself.

For the storage problem behind this model, read why .env files are not a complete secrets strategy.

Keep configuration explicit without keeping secrets in the project.

The project declares the runtime shape. Kimen supplies the local values only when a trusted process starts.

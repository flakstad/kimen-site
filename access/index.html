Your deployment credential ends up everywhere work happens.

Developers, CI jobs, workflows and agents all need to deploy. Each becomes another place where the same credential must be stored and protected.

The usual answer is to give every caller DEPLOY_TOKEN. It works—until access is spread across an organization and nobody has a simple way to see, change or revoke it.

There is a smaller way ↓

Every new caller becomes another credential holder.

The token spreads across developer laptops, CI settings, workflow connections and agent environments.

Each copy has to be installed safely and kept out of source control. Every local process that can read it effectively inherits its access.

If one copy leaks, the credential must be rotated everywhere. If someone leaves the team, you must know which keys and systems they carried.

And the token commonly permits much more than the one deployment everybody actually needed.

They don’t need the token. They need the deployment.

Give every caller the same small operation:

deploy-staging(revision)
Developers CI jobs Workflows Agents

Kimen keeps the credential, deployment target and provider setup. The callers can request a staging deployment and receive its result. They cannot reveal the token or turn it into another provider operation.

Give access to the operation—not the credential behind it.

What happens when Developer A deploys?

Developer A requests a concrete result.
deploy-staging(revision: "abc123")

Kimen checks the request.
The operation is fixed to staging. The revision must be valid. Developer A must be allowed to invoke it.

Kimen performs the deployment.
It uses the protected credential with the deployment workflow configured for this environment.

Developer A receives the outcome.

Give Developer D access without copying a credential.

Remove Developer B without rotating the token everywhere.

Change the deployment provider without updating every caller.

Audit the deployment that happened—not merely that a token was used.

The same problem appears wherever credentials stand in for a job.

instead of an observability API key

restart-staging(service)
instead of SSH or a cloud credential

trigger-backup(database)
instead of database administration access

Kimen already keeps runtime secrets out of the repository and supplies them only when a trusted application starts. Named operations take the next step: when someone only needs a result, Kimen can keep the credential to itself.

Your deployment credential ends up everywhere work happens.

Developers, CI jobs, workflows and agents all need to deploy. Each becomes another place where the same credential must be stored and protected.

The usual answer is to give every caller DEPLOY_TOKEN. It works. Then access spreads across the organization, and nobody has a simple way to see, change or revoke it.

There is a smaller way ↓

Every new caller becomes another credential holder.

The token spreads across developer laptops, CI settings, workflow connections and agent environments.

Each copy has to be installed safely and kept out of source control. Every local process that can read it effectively inherits its access.

If one copy leaks, the credential must be rotated everywhere. If someone leaves the team, you must know which keys and systems they carried.

And the token commonly permits much more than the one deployment everybody actually needed.

They don’t need the token. They need the deployment.

Give every caller the same small operation:

deploy_staging(revision)
Developers CI jobs Workflows Agents

Kimen keeps the credential, deployment target and provider setup. The callers can request a staging deployment and receive its result. They cannot reveal the token or turn it into another provider operation.

Give access to the operation, not the credential behind it.

Developer A requests a concrete result.
deploy_staging(revision: "abc123")

Kimen checks the request.
The operation is fixed to staging. The revision must be valid. Developer A must be allowed to invoke it.

Kimen performs the deployment.
It uses the protected credential with the deployment workflow configured for this environment.

Developer A receives the outcome.

An Action is not a script with a nicer name.

A script is code the caller runs. A Kimen Action is a request Kimen decides whether and how to carry out.

The project defines its public shape

The repository declares the operation and the input it accepts:

action deploy_staging(revision: git_sha)

This is an interface. It contains no token, deployment target or executable script, so it can travel with the project.

The environment defines what it actually does

A protected binding supplies everything the caller is not allowed to choose:

deploy_staging
  target      staging
  adapter     deployment_workflow
  credential  vault.deploy_token
  revision    commit_on_main

The binding lives outside the writable project. The credential remains in the local vault or an existing secret store.

Kimen handles every call

Kimen identifies the caller, checks access and validates revision. It resolves the protected binding, asks for approval when required, lets the trusted adapter use the credential, filters the result and records what happened.

The caller cannot substitute another command, target or credential.

The caller decides when. Kimen decides whether and exactly how.

Teams sync definitions, not credentials

The project declaration, trusted adapter and access rules are versioned. Kimen Teams sends signed definitions and access rules to developer machines and runners. Each environment keeps its own credential binding.

A changed Action definition or adapter does not silently inherit old approval. Local Kimen verifies the version before it performs the operation.

If the caller can edit the implementation and Kimen injects a token into it, it is still just a credential-bearing script.

A protected Action requires a trusted adapter outside the caller's control, constrained inputs, a fixed target and a bounded result.

The same problem appears wherever credentials stand in for a job.

inspect_logs(service, since)
instead of an observability API key

restart_staging(service)
instead of SSH or a cloud credential

trigger_backup(database)
instead of database administration access

Kimen already keeps runtime secrets out of the repository and supplies them only when a trusted application starts. Named operations take the next step. When someone only needs a result, Kimen can keep the credential to itself.

Adding another caller should not mean issuing another deploy key.

Kimen Core remains local, useful and open source. Kimen Teams coordinates which developers, CI jobs, workflows and agents may invoke each operation, in which environment and for how long.

Shared access rules. Approvals. Revocation. Identity. Audit.

Credentials and execution can remain in the environment you already trust. The team layer coordinates access; it does not need to become another hosted vault.

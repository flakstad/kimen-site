One deployment credential. Five copies.

To let the whole team deploy staging, the same reusable credential ends up on three laptops, in CI and inside an agent's environment.

Share the job, not the key.

The caller asks Kimen to deploy one revision. Kimen performs the fixed operation and returns the result.

Grant access without copying a credential.

Add a developer, workflow or agent to the operation. Nothing secret needs to be installed in its environment.

Remove access without rotating it everywhere.

Revoke the caller's permission. The credential behind the operation can remain where it is.

Change how deployment works in one place.

Move to another workflow or provider by changing the protected binding—not every script and laptop.

Record the work people actually performed.

Audit “deployed revision abc123 to staging,” rather than merely knowing that a token was used.

Kimen already lets a project declare DATABASE_URL while each environment supplies the actual value locally. Named operations extend the same model: the project declares deploy-staging(revision); the environment controls how it is performed.

The project carries the need. The environment keeps the authority.

Deployment is one example.

The same model can expose inspect-logs(service, since), restart-staging(service) or trigger-backup(database) without turning an arbitrary shell into a credential-bearing command.

One operation. Every caller. One place to govern it.

Local Kimen remains free and open source: vault, runtime configuration and local operations. Kimen Teams coordinates who may use each operation, in which environment and for how long—with shared rules, approvals, revocation and audit.

Let useful work happen without every developer and workflow inventing separate credentials, wrappers and security rules.

Most secret tools solve storage. Kimen solves exposure.

Encryption at rest is not the interesting part anymore. Kimen keeps secrets in a local vault, then projects them into runtime only when you ask and only in the shape the target process requires.

Explicit projection

Vault

Encrypted local storage

Trigger

Explicit user or automation intent

Shape

Env var, file, envfile, child process

Boundary

Only the named process gets the value

Case notes

Kimen is about runtime discipline, not just secret storage.

The unique move is not "put a secret in a vault." The unique move is "do not let that secret become part of the ambient weather of your shell, machine, or assistant session."

Not ambient

Avoid long-lived exports and copied `.env` files that outlive the task that needed them.

Not hosted-first

The hot path stays local. Team sync can exist without making local runtime depend on a control plane.

Not magic

Once you deliberately hand a secret to a process, that process has it. Kimen narrows exposure before that point.

Evidence

Three concrete moments where Kimen is better than habit.

One process, one env var

$ kimen run \
  --env SERVICE_API_TOKEN=demo_service_api_token \
  -- sh -lc 'echo "Token length: ${#SERVICE_API_TOKEN}"'

File only when the tool insists

$ OUTDIR="$(mktemp -d -t kimen-render.XXXXXX)"
$ kimen render --dir "$OUTDIR" \
  --file service-api-token.txt=demo_service_api_token

Assistant gets one key, not your whole shell

$ kimen run \
  --env PROVIDER_API_KEY=assistant_key \
  -- codex

Let Codex deploy staging without giving it your GitHub token.

Codex sends Kimen the commit it wants to deploy. Kimen checks that the repository, workflow and environment are allowed, calls GitHub with the protected token, and returns the deployment status.

A GitHub token gives the agent more than one staging deploy.

Even when the token is hidden from the model, a process using it may be able to perform every operation the token permits. Kimen exposes only the job you chose.

Pass the GitHub token to a process

That process can attempt anything the token allows.

  • The token is present in the process
  • The process chooses which GitHub API call to make
  • A mistake can affect more than staging

Let Kimen call GitHub

Kimen accepts only a commit for the configured staging workflow.

  • The agent never receives the token
  • Repository, workflow and environment are fixed
  • The agent gets status and a receipt

You configure the allowed job. The agent can only ask Kimen to run it.

The configuration that contains the repository, workflow and credential stays outside the agent-editable project.

The agent sends

Deploy commit 8d2f74a to staging.

It can choose the commit. It cannot choose another repository, workflow or environment.

Kimen checks and runs

Repository: acme/app. Workflow: deploy-staging. Environment: staging.

Kimen verifies the input, adds the GitHub token and makes the fixed request.

Codex gets “deployment started.” It never gets the token or a general GitHub client.

Use the same pattern for other jobs you still do manually.

Kimen must know the exact service and request it is allowed to perform. It does not run an arbitrary shell command with a secret attached.

Start here if you want to use Kimen as a local-first secrets tool for ordinary applications and scripts.

Kimen stores secrets in an encrypted local vault and lets you project them into runtime only when you explicitly ask. The main idea is simple: keep secret storage separate from the process that consumes the secret, and prepare env or files only at launch time.

Getting Started

A short path through the core workflow: initialize a vault, store a secret, and use that secret for a single command. 

kimen vault init
kimen secret set demo_service_api_token
kimen run --env SERVICE_API_TOKEN=demo_service_api_token -- ./your-command
  1. kimen vault init creates the encrypted local vault.
  2. kimen secret set NAME stores a named secret in that vault.
  3. kimen run projects the value only for the child process you start.

Core Commands

kimen run

Run a child process with projected env vars, files, or stdin. This is the primary command for development and automation. 

kimen run --env API_KEY=api_key -- curl -H "Authorization: Bearer $API_KEY" https://example.com

kimen render

Write projected files into a directory when a tool wants a file path instead of an env var. 

OUTDIR="$(mktemp -d -t kimen-render.XXXXXX)"
kimen render --dir "$OUTDIR" --file cfg.txt=api_key

kimen envfile

Generate a `KEY=VALUE` envfile for supervisors or deploy scripts. 

kimen envfile --env SERVICE_API_TOKEN=demo_service_api_token --out .env.runtime

kimen plan

Print the projection plan without printing secret values. Useful for review and automation. 

kimen plan --profile dev
kimen plan --profile dev --json

Value Sources

On the right-hand side of an env, file, or stdin mapping, Kimen normally expects a vault secret name. It also supports a few explicit source forms.

  • secret:name or bare name: read from the local vault
  • const:value: use a literal value
  • exec:command...: run a local command and use its stdout 
kimen run \
  --env SERVICE_API_TOKEN=secret:demo_service_api_token \
  --env REGION=const:eu-north-1 \
  --env TOKEN=exec:./scripts/derive_token.sh \
  -- your-command

Maps And Profiles

Use .kmap files and named profiles when you want repeatable intent instead of repeating flags on every command. 

mkdir -p .kimen/profiles
cat > .kimen/profiles/dev.kmap <<'EOF'
env SERVICE_API_TOKEN=demo_service_api_token
file service-api-token.txt=demo_service_api_token
EOF

kimen map lint --profile dev --strict
kimen plan --profile dev
kimen run --profile dev -- ./your-command

Current Sync Scope

Kimen supports encrypted bundle sync through fs and git remotes. The main surfaces are kimen remote ... and kimen sync ....

  • kimen remote add|get|set|list|rm
  • kimen sync
  • kimen sync init|preflight|status|conflicts|changes|push|pull|resolve|reset-baseline|unlock|restore

For most users, the important point is that sync does not change the local runtime model. Secrets are still projected locally when you ask.
